# إعداد لوحة تحرير الشفرة

تضيف هذه المرحلة لوحة تحرير على `/admin` وقاعدة Supabase ومكتبة ملفات، مع بقاء الصفحات العامة ثابتة وسريعة. لا تُقرأ قاعدة البيانات من الزائر عند عرض المقال؛ بل يُصدّر البناء السجلات المنشورة والمفهرسة فقط إلى `src/data/cms-content.json` ثم يحولها إلى صفحات ثابتة.

## 1. إنشاء المشروع المجاني

1. أنشئ مشروعًا في Supabase.
2. من **Authentication → Providers** أبقِ البريد وكلمة المرور، وعطّل التسجيل العام. لا توجد شاشة تسجيل في الموقع.
3. نفّذ `supabase/migrations/202608180001_content_platform.sql` في SQL Editor. ينشئ الملف الجداول، RLS، سجل المراجعات، سجل التدقيق، وعاء `media` وسياسات التخزين.
4. من **Authentication → Users** أنشئ مستخدم المالك يدويًا.
5. رقِّ المستخدم الأول فقط بعد استبدال UUID:

```sql
update public.profiles
set role = 'admin', display_name = 'مالك الموقع'
where id = 'USER_UUID';
```

الحساب الجديد يبدأ دائمًا بدور `viewer` ولا يستطيع الكتابة. الأدوار هي:

- `viewer`: حساب موجود بلا صلاحية تحرير.
- `author`: ينشئ محتوى ويعدّل مسوداته، ولا ينشره.
- `editor`: يراجع وينشر ويحدّث المحتوى والوسائط والتحويلات.
- `admin`: يدير الأدوار والحذف وسجل التدقيق.

## 2. متغيرات البيئة

انسخ أسماء المتغيرات من `.env.example` إلى إعداد الاستضافة. القيمتان البادئتان بـ`VITE_` عامتان ومخصصتان للمتصفح، وتحمي RLS البيانات حتى مع ظهورهما.

`SUPABASE_SERVICE_ROLE_KEY` سر خادم ذو صلاحية عالية:

- لا تضعه في `.env` ملتزم إلى Git.
- لا تسمّه باسم يبدأ بـ`VITE_`.
- لا تستخدمه داخل `src/`.
- خزّنه في Secrets الخاصة بالبناء/الاستضافة فقط.

في نشر الإنتاج اجعل `CMS_SYNC_REQUIRED=true` حتى يتوقف البناء إذا تعذر تصدير المحتوى بدل نشر نسخة قديمة بصمت. التطوير المحلي بلا أسرار يحافظ على الكاش المتتبع.

## 3. دورة التحرير والنشر

1. افتح `/admin` وسجّل بالحساب الذي أنشأه المالك.
2. أنشئ مسودة وحدد النوع والمسار واللغة والعنوان والوصف والنص.
3. أضف مصدرًا واحدًا على الأقل بصيغة JSON. مثال:

```json
[
  {
    "label": "دعم الشركة المصنّعة",
    "url": "https://example.com/official-support",
    "sourceType": "manufacturer-support",
    "pageReference": "القسم 4"
  }
]
```

4. الصور تحتاج وصفًا بديلًا واسم الترخيص أو عبارة `ملكية الشفرة` قبل رفعها. الحد 8 ميجابايت، والأنواع المقيدة مذكورة في الهجرة.
5. حوّل الحالة إلى `review` للمراجعة. المحرر يطابق المصدر والموديل والروابط وحقوق الوسائط.
6. يختار المحرر `published` ويحدد السماح بالفهرسة ثم يحفظ. الحفظ في القاعدة وحده **لا ينشر الصفحة للعامة فورًا**.
7. شغّل نشرًا مراجعًا عاديًا. ينفذ `npm run build` أولًا `npm run cms:sync`، ثم يبني الصفحة الثابتة ويضيف الصفحات المؤهلة إلى مخرجات SEO.

لا توجد مهمة زمنية تغيّر المسودة أو تنشئ صفحات من تلقاء نفسها. يستطيع المحرر تحديد «موعد الإتاحة»؛ عندئذ لا يصدّر `cms:sync` السجل قبل الموعد، ويلزم تشغيل بناء نشر مراجع بعده. هذا يحافظ على التحكم البشري ولا يوهم بوجود نشر لحظي بلا عملية deploy.

## 4. التنسيق الآمن

المحرر الحالي يدعم جزءًا مقيدًا من Markdown:

- `##` عنوان قسم.
- `###` عنوان فرعي.
- `-` أو `*` عنصر قائمة.
- بقية الأسطر فقرات نصية.

HTML الخام لا يُفسّر ولا يُمرر إلى `dangerouslySetInnerHTML`. هذه قاعدة أمان متعمدة.

## 5. النسخ الاحتياطي والاستعادة

- فعّل النسخ الاحتياطية المتاحة في خطة Supabase، ونزّل تصدير PostgreSQL دوريًا خارج المستودع.
- يحتفظ `content_revisions` بلقطة قبل كل تعديل. واجهة الاستعادة المرئية مرحلة لاحقة؛ يستطيع المسؤول استعادة لقطة بعد فحصها من SQL أو إضافة الواجهة دون تغيير المخطط.
- يحتفظ `audit_log` بعمليات المحتوى؛ قراءته محصورة بالمسؤول.
- اختبر استعادة نسخة في مشروع منفصل قبل الاعتماد عليها.

## 6. سياسة المسارات والتحويلات

لا تحذف URL قديمًا أو تحوله إلى الرئيسية تلقائيًا. يسجل جدول `redirects` القرار والدليل والمراجع، لكنه لا يصبح فعالًا حتى يراجعه مسؤول ويُصدَّر إلى إعداد الاستضافة. الحالات المقبولة: إبقاء/تحديث، إعادة كتابة، دمج، `noindex`، أرشفة، 301 إلى بديل مكافئ فعلًا، أو 404/410 حقيقي.

## 7. حدود الخطة المجانية

البداية ممكنة على الخطط المجانية مع الدومين المملوك. لكنها ليست وعدًا بتشغيل قاعدة ووسائط عالمية بلا حدود: زيادة الزيارات، التخزين، نقل الصور، النسخ الاحتياطية أو عمليات البناء قد تتطلب خطة مدفوعة. راقب الاستخدام شهريًا واضغط الصور ولا ترفع ملفات بلا حقوق أو حاجة تحريرية.
